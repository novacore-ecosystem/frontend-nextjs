## Key Learnings

- **Project:** frontend-nextjs — NovaCore Next.js UI ecosystem. `packages/shadcn` = `@novacore/frontend-next-shadcn`, `apps/playground` = demo consumer. Governed by a detailed system-prompt spec (see original mission) covering: hide shadcn/Radix/Tailwind entirely behind NovaCore's own contracts, per-file RSC client/server boundaries, ship precompiled CSS so consumers never touch Tailwind.
- `@novacore/frontend-foundation` (sibling repo at `../../frontend-foundation` relative to this repo's root, i.e. `FrontEnd/Common/frontend-foundation`) is framework/UI-agnostic — has `PaginatedResult`/`PAGINATION_DEFAULTS` (1-based `pageNumber`, canonical shape for every NovaCore backend list endpoint) and an `authorization` module (`Permission`, `hasPermission`, etc.). Consume it, never refactor it. Referenced via `"file:../../../frontend-foundation"` in `packages/shadcn/package.json` since it isn't published to a registry — not a pnpm workspace member (lives outside this repo's `pnpm-workspace.yaml` scope entirely).
- `tsup` + esbuild **strips `"use client"` directives** during bundling (`bundle: true`/code-splitting) because it's not part of the ECMAScript spec — esbuild treats the bare string-literal expression statement as dead code. Fix: `bundle: false` in tsup config so every source file transpiles 1:1 into `dist/` (no chunk merging), which preserves the directive per-file naturally. A `scripts/postbuild-use-client.mjs` safety net also exists (reads each `.js.map`'s `sources` to detect which compiled files trace back to a `"use client"` source file, and re-prepends the directive if missing) — currently patches 0 files since `bundle:false` already handles it, but keep it as a guard.
- Tailwind CSS variables for this package are prefixed `--nc-*` (not the bare `--background` etc. shadcn convention) to avoid colliding with a consuming app's own CSS variable names when the compiled `styles.css` is imported into the app's global scope.
- DataTable's own `DataTablePaginationState` uses `pageNumber` (1-based), matching `@novacore/frontend-foundation`'s `PaginatedResult` convention — do not use 0-based `pageIndex`, it would need a translation layer at every real API call site.
- **`packages/mui` (`@novacore/frontend-next-mui`)** — second UI-library adapter, client-facing (storefronts/marketing/product pages), fully independent dependency graph from `packages/shadcn`. Stack: `@mui/material` 9.3.1, `@emotion/react`+`@emotion/styled`, `@mui/material-nextjs` (official `AppRouterCacheProvider` for Emotion SSR under App Router), `@mui/icons-material`, `motion` (framer-motion's rebrand, used only by the optional FadeIn/SlideIn/ScaleIn wrappers). Uses `tsup --bundle=false` + the same `postbuild-use-client.mjs` pattern as shadcn (copied verbatim — script is generic).
- **MUI's own npm dist already ships `"use client"`** on every interactive component (verified directly in `node_modules/.pnpm/@mui+material@.../Typography/Typography.js` etc.) — so our own wrapper files only need the directive when *they themselves* use hooks (useState, the theme context, etc.), not merely because they render an MUI component. A wrapper that just composes already-client MUI primitives (Card, Box, Heading, Text, layout/typography/most navigation+hero components) stays server-safe.
- MUI Stack's prop surface changed vs. older MUI versions/assumptions: `alignItems`/`justifyContent`/`flexWrap` are **not** auto-forwarded as system-style props on Stack in 9.3.1 — they leak onto the DOM node as invalid HTML attributes if passed directly. Route them through `sx` instead (see [[bug-003 in buglog.json]]).
- **RSC rule that bites UI-library wrapper components specifically:** a Server Component can render a Client Component with serializable props, but NOT a function value — including one created *inside a plain (non-"use client") wrapper function* that itself has no hooks. Any prop-forwarding wrapper (`<TextField onChange={...}>` etc.) that unconditionally builds `(e) => onChange?.(e.target.value)` and passes it to an underlying MUI/Radix client component will crash the moment it's used from a Server Component without the caller supplying `onChange` (e.g. a read-only `<Rating>` inside a static product page) — see [[bug-002 in buglog.json]]. Rule of thumb: only construct the closure when the corresponding callback prop was actually provided; otherwise forward `undefined`.
- `@novacore/frontend-foundation`'s `formatCurrency` (Intl-backed, CLDR fraction-digit/symbol rules) powers the MUI package's `Price` component — same "consume the foundation, don't reinvent formatting" pattern as shadcn's `fromPaginatedResult`.
- Native `<input type="date">` (wrapped as MUI TextField) is used for DateField/DateRangeField instead of `@mui/x-date-pickers` + a date-adapter — avoids a heavyweight new dependency for phase 1; documented as a limitation, upgradeable later.

## Do-Not-Repeat

<!-- Mistakes made and corrected. Each entry prevents the same mistake recurring. -->
- [2026-08-11] First attempt bundled `packages/shadcn` with tsup's default (`bundle: true`, code-splitting, 5 barrel entry points). This merged client- and server-safe components into shared chunks and esbuild silently dropped every `"use client"` directive — the compiled package had *zero* `"use client"` markers anywhere, which would break RSC boundaries in the consuming Next.js app the moment a Server Component imported an interactive component (AdminLayout's `useState`, etc.) without its own client wrapper. Fixed by switching to `bundle: false` (one output file per source file) plus a sourcemap-based postbuild safety net. Always verify directive survival in `dist/` output directly (`head -c N dist/**/*.js`) after building any React component library with tsup/esbuild — don't assume it "just works". Applied `bundle:false` to `packages/mui` from the start based on this lesson.
- [2026-08-12] `packages/mui`'s form/data wrapper components (TextField, Select, Checkbox, Rating, etc.) initially always built an inline onChange closure regardless of whether the caller passed one, which crashed `next build` (`Error: Event handlers cannot be passed to Client Component props`) the first time a display-only usage (`<Rating readOnly />` inside `ProductCard` on a Server Component page) hit production prerendering — `next dev` did NOT catch this until the specific route was requested. Always run a full `next build` (not just `next dev`) before declaring a component library's playground integration verified; RSC serialization errors during static generation don't always surface in dev mode until you visit the exact route.
- [2026-08-12] Assumed MUI Stack forwards `alignItems`/`justifyContent`/`flexWrap` as system props the way Box does — wrong for `@mui/material@9.3.1`, they leak onto the DOM as invalid attributes (console warning, not a crash). Caught it by reading the `next dev` terminal log after exercising every playground route, not just checking HTTP status codes. Don't assume an MUI subcomponent's prop surface without checking the installed version — check `node_modules` source or the browser console, not memory of older MUI API docs.

## Decision Log

<!-- Significant technical decisions with rationale. Why X was chosen over Y. -->
- [2026-08-11] Theme resolution is done in JS (`resolveTheme()` → CSS custom properties applied via `AdminProvider`'s `useEffect`), not via static CSS classes per base×color combination. Rationale: a static approach would need 5 bases × 8 colors × 4 radii × N styles of prebuilt CSS variants (combinatorial explosion), whereas resolving in JS keeps `dist/styles.css` small (one token layer) and matches the spec's "Config → Resolved Theme → Semantic Tokens → CSS Variables" diagram exactly. Tradeoff: theme applies post-hydration (documented flash-of-default-theme limitation in README), no SSR no-flash script yet.
- [2026-08-11] DataTable was built from scratch (no TanStack Table dependency) specifically to guarantee zero underlying-table-library type leakage and to avoid pulling in a large new dependency for phase 1. Covers sorting, row selection, pagination, loading/empty/error states, bulk actions slot — no column resizing/reordering/virtualization yet.
- [2026-08-11] Package uses Tailwind v3 (not v4) for the CSS build — v3's PostCSS/CLI pipeline is simpler to point at a package's own `src/**/*.{ts,tsx}` and ship a static compiled `dist/styles.css`, which is the "package-owned CSS" requirement from the spec (consumers must not need Tailwind installed or configured).
- [2026-08-12] `packages/mui` does NOT ship a compiled CSS file the way `packages/shadcn` does — MUI's own theme/Emotion system generates styles at runtime via `ClientProvider`'s `AppRouterCacheProvider` + `ThemeProvider` + `CssBaseline`, so there's nothing static to precompile. This is an intentional divergence from the shadcn package's architecture per the "respect each UI library's own architecture, don't force Tailwind/CSS-variable patterns onto MUI" mission rule.
- [2026-08-12] Chose 8 named presets (ocean/indigo/emerald/sunset/rose/violet/slate/neutral) as full identities (base neutral tone + primary/secondary hue bundled together) rather than shadcn's separate base-palette × accent-color composition matrix — simpler for a client-facing/marketing-focused package where a preset is meant to be a complete "brand personality" pick, not a fine-grained palette experiment. `color`/`style`/`radius`/`density` remain independently overridable on top of a chosen preset.
- [2026-08-12] DataTable-equivalent decision: did not add a generic admin `DataTable` to `packages/mui` — this package is explicitly client-facing/storefront-focused per the mission (admin density belongs to `packages/shadcn`). Data display favors `ProductGrid`/`Stat`/`Rating` instead.
